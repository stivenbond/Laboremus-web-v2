## Workflow of the internal platform

each user of the platform has a role which define what he can do. the roles are: Editor-in-Chief, overseer, writer, editor, formatter, publisher, approver, who all reside in the "user" scope of things and the admin which is in charge of the whole platform technically. the admin assigns the approver, publisher and overseer, and can manage all the users and monitor the platfrom. The overseer assigns the editor-in-Chief, formatters, editors and writers and can add new users to the platform. 
the workflow and all documentation is saved in the folowing manner. when working on something the user has the ability to work on an autosaved draft and when ready can commit to a version and then that version can be reworked and progress continuously to new versions (similar to git commits) and a version can be sent for approval/review. every review can be accepted or rejected with or without comments and if rejected the user who it was sent to will be notified and can rework the document. a document can undergo multiple reviews before it is accepted. the comments and all that is in the review/approval is saved as documentation for that version. 
the editor in chief creates briefs for the articles and assigns writers and editors to each of the briefs(following the document draft/version cycle described above for the briefs). the assignments are pushed out in bulk but edits can be made to assigned briefs and aditional briefs can be added or removed at any moment. before writers can start working on the briefs, they have to be reviewed by the overseer (following the review/rework cycle described above). upon acceptance by the overseer, writers can start working on the briefs (following the document draft/version cycle described above for the briefs). Once a writer is done with the brief they send it to the pre-assigned editor of that brief for review (following the document draft/version cycle described above for the briefs). Once the editor is done with the brief they send it to the overseer. the editor in chief can view all briefs and their progress all the time and can interject in any part of the process and can reassign tasks to other users but the authorship trail is preserved. While writing/editing the article, writers and editors have access to an AI tool that upon commiting a new version reviews the article and provides recommendations which aid the user in refining their articel further in the writing or editing stage. the ai tool doesn't stop a user from submitting a version for approval. the overseer and editor in chief can edit the article submitted for approval directly (although only the overseer can approve an article for formatting) or reject it with comments.
when an article is approved for formatting by the overseer, the formatters edit the text with markdown and markup annotations and syntax and include images and text styling (following the document draft/version cycle described above for the briefs). While working on a draft they can see a preview of the final result and when ready they can send it for approval to the overseer (following the review/rework cycle described above). the overseer can approve or reject the brief with comments and the formatter can make the changes and send a new version for approval to the overseer. once an article is approved for publishing by the overseer it is sent to the publisher for scheduling the article to a certain date or to the approver who can aproove the article and the publishing to the public blog then happens in automation or can reject the article with or without comments and send it back to the overseer and editor-in-chief to make the nescessary changes who can send a new version to the approver ( without changing the publishing schedule or formatting annotations and if the submission date of the new version is past the scheduled publishing date it is published immedeately upon aproval by the approver of the new version.)
the public part of the platform is blog like and is controlled by the publisher, overseer and editor in chief and any changes have to be approved by the overseer or publisher. the public blog can be accessed by the public. 
all events ( assignments, rejections, approvals, etc.) are sent as notifications to the users who have interest in them. 

## Technical implementation details 
- the database is handled by postgres and drizzle db 
- the frontend os using shadcn ui and nextjs
- effect.ts is used thoughout the app for everything
- the blog is public while the admin page is a protected route
- the authentication is handled by betterauth
- the development of the app should be kept inside a devcontainer
- the app is fully dockerized and should be able to run locally with docker compose
- use the effect.ts library for all state management and side effects
- use the context system of effect.ts to manage the state of the application
- use opentelemetry via the effect.ts library for logging, tracing and metrics collection.
- the app should be PWA compatible.
- use the latest stable versions of all libraries and frameworks.
- for AI usage the project integrates with an external REST API that uses keys to give the whole platform access to different AI models.
